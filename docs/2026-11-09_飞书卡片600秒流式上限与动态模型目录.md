# 飞书卡片 600 秒卡死真因 + 模型目录动态化（2026-11-09）

## 一、600 秒卡死：真因是飞书流式窗口，不是本地超时/时间格式

### 实测（不猜测）
建两张**未发送**的卡片实体做探针：

| 时间 | A（不重新开启） | B（480s 时 PATCH settings 重新开启） |
|---|---|---|
| 60s / 300s / 480s / 570s | PUT 200 success | PUT 200 success（与 A 相同）|
| 630s | **PUT 200850 card streaming timeout** | **同样 200850** |
| 700s | 300309 streaming mode is closed | 同样 300309 |

结论：**流式模式打开满 600 秒被飞书自动关闭**。

第二个探针（未发送卡片，到点后再重开）推翻了「无法重新打开」：

| 时间 | 操作 | 结果 |
|---|---|---|
| 620s | PUT | 200850 card streaming timeout |
| 620s | 关闭**之后** PATCH settings streaming_mode=true | **success** |
| 640s / 900s | PUT | **success** |

所以：**关闭前重开无效（B 卡），关闭后重开有效**。
此后所有「流式更新文本（PUT element content）」全部失效 —— 这就是用户看到的
「⏱️ 600s 之后卡片不动、正文永远出不来」。

对照真实日志：23:13:40 建卡，600 秒后 `cardkit_events.log` 里 on_thinking 仍在涨
（超过 5,024 字），但界面文字停在 5,024 字 —— 与 600 秒窗口完全吻合。

**此前把原因归到「秒/分秒格式混用」是错的**，那只是显示不一致，不会丢掉正文。

### 修复（cardkit.py）
- PUT 返回 200850/300309 → `_rearm_streaming()` 重开（共用卡片全局 sequence）→ 重发被拒的那一笔，
  流式继续逐字推送。每卡最多重开 30 次（≈5 小时）。
- 不再按本地计时在 595 秒提前停 PUT（窗口从「最后一次打开」起算，本地计时会误判）。
- 只有重开失败、或重开后重发仍被拒，才置 `_stream_closed`，降级为**整卡 `PATCH /im/v1/messages/{id}`**
  续写（不受流式窗口限制），内部 6 秒节流。
- 30 秒心跳在关闭窗口内直接推整卡；`finalize()` 额外强制刷一次，保证最终正文与
  「✅ 回合完成」一定落屏。
- 时间格式统一为 `{m}m {s}s`（仅美观）。

## 二、模型列表不再硬编码，直接读 Hermes 自己的目录

`plugins/platforms/feishu/feishu_setup_cards.py` 重写：
- 唯一数据源 = `hermes_cli.model_switch_providers.list_picker_providers()`（原生 /model
  picker 同一个调用）。新增 provider / 新增模型 → 卡片自动出现，**不用改代码**。
- 目录缓存（`remember_catalog` / `cached_catalog`）：卡片回调必须 3 秒内响应，只读缓存；
  picker 发送路径用 `asyncio.to_thread` 刷新。
- 网关传进来的 picker 目录被 `max_models=50` 截断，检测到 `total_models > len(models)`
  时自动重载完整目录。
- 聚合渠道（OpenRouter / Nous）按「模型家族」收敛：去掉版本号/日期快照与 `:free`/`:batch`
  /`-fast`/`-flex`/`~` 变体，保留目录自身排序（最新在前），每渠道上限 30。
- 过滤非对话端点（tts/asr/realtime/embed/rerank/audio/image）。
- 每个选项值带渠道：`<slug>::<model>`（表单提交时 `action.value` 为空，值本身必须带渠道）。
- 删除 `CHANNEL_MODELS` / `CHANNEL_DEFAULT_MODELS` / `CHANNELS` / `spark` 假渠道。

### 实测（真实目录）
9 个可用渠道：antigravity-manager 11、nous 30(旗舰收敛)、openrouter 30(旗舰收敛)、
workbuddy 21、dashscope 14、zai 14、apikey-fan 9、openai-codex 6、deepseek 2。
最大卡片 tags=71 / 8.3KB（飞书限 200 元素、30KB）。

## 三、表单提交必须「写入 + 回读校验」

旧实现手搓 override dict（只有 model/provider，没有 base_url/api_key），写内存后就算成功；
实际运行时 `_apply_session_model_override` 会跳过 None 字段，凭据还是默认渠道的。

新实现 `_apply_route_to_session()`：
1. `session_store.set_model_override(skey, {model, provider})`
2. 清空内存 override → `gw._rehydrate_session_model_override(skey)`（与重启后同一条路径，
   api_key/base_url 由 provider 自己解析）
3. 回读 `_session_model_override` 校验 model；再 `_resolve_runtime_agent_kwargs_for_provider`
   探测凭据
4. 失败就在卡片上写 ⚠️，不再「点了就算成功」

新话题的 session key 一律用 `gw._session_key_for_source(source)` 生成（不再手拼
`agent:main:feishu:dm:chat:thread`）。

`/model` 提交优先走网关原生 picker 回调（解析 provider、写 DB、next-turn note、驱逐 agent 全走官方路径）。

## 五、已知边界
- 重开在**未发送**的卡片实体上实测有效；已发送的消息卡尚未在真实长任务中验证（需重启网关后观察
  `cardkit_events.log` 的 `stream_rearm ok=true`）。
- 重开失败时降级为整卡 PATCH，每 6 秒刷新一次，不是逐字打字机，但不丢内容。
- `/usr/bin/python3` 缺 aiohttp/dotenv，系统 Python 跑测试会大面积失败；一律用 `scripts/run_tests.sh`。

## 六、教训
- 探针只测了「到点前重开」就下了「无法重开」的结论，是错的。限制类结论必须正反两个顺序都测。
