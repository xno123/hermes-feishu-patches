# 飞书本地补丁维护手册（升级防错）

本机飞书通道跑的是**源码补丁**，不是插件。`hermes update` 会覆盖 `gateway/` 与
`plugins/platforms/feishu/` 下的核心文件。本手册是更新前后的唯一执行依据，
不靠记忆、不靠手工从备份挑文件。

调研与逐次修复的时间线见同目录 `2026-11-07_dsh-feishu-plugin借鉴评估.md`；
本文只管「怎么让补丁在更新后活下来」。

## 一句话

更新后：`bash ~/.hermes/scripts/feishu_patch_guard.sh` → 有 FAIL 就加 `--fix`
→ 复检 `0 FAIL` → **用户在外部终端重启网关** → 实机验四项。

## 补丁基线

- 打补丁时 HEAD：`2bd378ed1b8d6bf2192cb26e0a55ff3091e6bd19`（Hermes v0.23.0）
- 三套能力：① 分话题（主框消息自动开话题 + 话题=独立 session）；
  ② CardKit 2.0 流式卡；③ 卡片溢出修复（标题对齐 / 思考流 / 工具 tee / 分槽 / 封卡时机）
- 门控（`.env`）：`FEISHU_CARDKIT=1`、`FEISHU_THREAD_REPLY=true`、
  `FEISHU_DM_TOPIC_REPLY=true`

## 会被 update 覆盖的文件

tracked（8 个）：

- `plugins/platforms/feishu/adapter.py` ← **三套补丁共用，最危险**
- `plugins/platforms/feishu/plugin.yaml`
- `gateway/run_turn_runner.py`
- `gateway/run_turn_progress.py`
- `gateway/stream_consumer_transport.py`
- `tests/gateway/test_setup_feishu.py`
- `website/docs/user-guide/messaging/feishu.md`
- `website/i18n/zh-Hans/docusaurus-plugin-content-docs/current/user-guide/messaging/feishu.md`

untracked（update 通常不删，但 `git clean`／手工恢复会丢，共 5 个）：
`plugins/platforms/feishu/feishu_thread_reply.py`、`plugins/platforms/feishu/cardkit.py`、
`gateway/cardkit_bridge.py`、`tests/gateway/test_feishu_thread_reply.py`、
`tests/gateway/test_cardkit_scope.py`

## 更新前

1. `cd ~/.hermes/hermes-agent && git status --short` 存档。
2. 确认 `~/.hermes/patches/` 与 `~/.hermes/scripts/` 完整（见下「产物清单」）。
3. 记下 `git rev-parse HEAD`。

## 更新后（按顺序，别跳）

1. `bash ~/.hermes/scripts/feishu_patch_guard.sh`
   - 判据：`40 PASS / 0 FAIL / 0 WARN`，且回归测试行显示 `32 passed`。
2. 有 FAIL → `bash ~/.hermes/scripts/feishu_patch_guard.sh --fix`
   - 固定顺序：先分话题（逐文件块 `git apply`，安全）→ 再卡片（整文件覆盖 `after/`）。
   - **HEAD 与基线不一致时脚本会 WARN 并跳过卡片整文件覆盖**：因为覆盖可能抹掉上游新代码。
     先人工看 `git diff --name-only <基线> HEAD -- <7 个补丁文件>`，确认上游没改这些文件后，
     再手动 `bash ~/.hermes/scripts/apply_feishu_cardkit_fix.sh`。
3. 再跑一次 guard，确认 `0 FAIL`。
4. **用户在自己的终端执行 `hermes gateway restart`**（agent 不能重启自己的网关；
   未重启前不要宣布生效）。
5. 实机验四项：主框发消息自动开话题／卡片标题=该会话真实 title／多工具长任务里
   工具调用持续追加进折叠框／只在真正回合结束出现「✅ 回合完成」。

## 手动重打（不用 guard 时）

```bash
bash ~/.hermes/scripts/apply_feishu_topic_thread.sh    # 幂等：逐文件块判断，未打→apply，已打→跳过
bash ~/.hermes/scripts/apply_feishu_cardkit_fix.sh     # 整文件覆盖 after/，自带落点校验+py_compile+单测
```

两个脚本都必须**真跑两次**（新状态 + 幂等状态）才算可用 —— 本机已踩过
heredoc 把 `\S` 写成 `\\S`、以及忘了 `open(...).read()` 把路径当内容去 split 的坑，
`bash -n` 查不出来。

## 回滚

| 目的 | 命令 |
|---|---|
| 只关卡片（保留代码） | `.env` 设 `FEISHU_CARDKIT=0` |
| 回退卡片修复到修前 | `bash ~/.hermes/scripts/rollback_feishu_cardkit_fix.sh` |
| 完整回滚 CardKit 到修前 + 关门控 | `bash ~/.hermes/scripts/rollback_cardkit.sh`（已修正，不再 `git checkout`） |
| 只关话题 | `.env` 两个 THREAD 开关设 `false` |

⚠️ `rollback_feishu_thread.sh` 已废弃为拒绝执行的提示脚本：旧版 `git checkout --
adapter.py` 会连带抹掉卡片修复。任何按文件 `git checkout` 的回滚都不要再跑。

## 产物清单（更新前先确认在）

| 路径 | 作用 |
|---|---|
| `~/.hermes/scripts/feishu_patch_guard.sh` | **统一入口**：40 项体检 + `--fix` + 基线漂移告警 |
| `~/.hermes/patches/feishu_topic_thread.patch` | 分话题独立补丁（17 hunks，剔除卡片 2 个 hunk） |
| `~/.hermes/patches/feishu_topic_thread_files/` | 两个 untracked 新文件副本 |
| `~/.hermes/scripts/apply_feishu_topic_thread.sh` | 分话题幂等重打 |
| `~/.hermes/patches/cardkit_fix_20261107/{before,mid,after}/` | 卡片修复前／小修前／最新完整文件副本 |
| `~/.hermes/scripts/apply_feishu_cardkit_fix.sh` | 卡片补丁幂等重打（7 文件覆盖） |
| `~/.hermes/scripts/rollback_feishu_cardkit_fix.sh` | 卡片补丁回滚 |
| `~/.hermes/scripts/rollback_cardkit.sh` | 完整回滚（已修正） |

回归测试（每次都要 45 passed）：
`test_feishu_thread_reply.py`(11) + `test_setup_feishu.py`(9) + `test_cardkit_scope.py`(25)

## 踩过的坑（下次别重犯）

| 现象 | 根因 | 防错 |
|---|---|---|
| 升级后向导不再写 `FEISHU_THREAD_REPLY`、3 个测试红 | 手工从备份恢复 adapter.py 时漏了 `interactive_setup` 那个 hunk（9→8） | 别手工挑文件；guard 专门检这一项 |
| docs / setup 测试 10 个 hunk 丢失 | 同上 | 独立补丁 + 逐块重打脚本 |
| 回滚卡片后话题能力一起没了 | `rollback_cardkit.sh` 整文件 `git checkout -- adapter.py` | 改用 `rollback_feishu_cardkit_fix.sh`（cp before/） |
| 卡片标题串台 | `session_title` 按 chat_id 取「最近一条」 | `session_key → thread_id → chat_id` 三级精确查 |
| 思考过程折叠框空 | `push_thinking()` 零调用 | 接 `agent.reasoning_callback` |
| 工具调用折叠框空 | tee 放在 `progress_queue` guard 之后，飞书 `tool_progress=false` → queue=None 提前 return | tee 移到 guard 前 |
| 卡片只收第一轮，之后全溢出 | `finalize=True` 是段落封版（工具边界／拆块），不是回合结束；见 finalize 就封卡 | 透传 `is_turn_final`，只在它为真时封卡 |
| 又变成「回合完成 · 181s」但 turn 跑了 640s | `adapter.send()` 的首次发送／长任务心跳也走 send，旧逻辑见 send 就封卡 | streaming ON 时 send 一律不封卡，只由 `on_edit(is_turn_final=True)` 封卡；心跳写状态行、播报进思考框 |
| 弹出卡片但正文是「（等待回答…）」 | 最终答复走 `adapter.send()` 而非 `edit_message()`；补修 3 把 send 文本全塞进 think_text，从不写 main_answer | send 一律写 main_answer（心跳只写状态行），streaming ON 仍不封卡；加 `cardkit_events.log` 事件流水 |
| 标题错配 + 思考全量 + 工具只显一轮（三个同时） | 元素写入路径分散无协调、无显示策略、标题依赖异步落库的 state.db | 2026-11-07 系统性重构：单一状态机 `CardKitStream` + `ElementPolicy` + 统一 `render()` + `title_hint`；详见 [[2026-11-07_飞书卡片架构排查与重构方案]] |
| 长任务卡片正文一直是中间播报、看不到结论 | `on_send()` 把工具间 commentary / 首帧预览也当最终答复写 `main_answer`，35 分钟里被 16~45 字短句反复覆盖；封卡靠兜底定时器再延迟 3.5 分钟 | 2026-11-07 补修 6：用 gateway `metadata.notify` 区分最终答复，中间播报只写 `status_line`，绝不碰正文 |
| 网关 `-I` 下 import 静默失败 | 裸 `try/except: pass` 吞掉 `ModuleNotFoundError`（ruamel 在 pm-runtime venv） | 零依赖桥按文件路径加载；验证时补 venv site-packages |
| 本地全过、生产没反应 | 系统 python 与网关 `-I` 依赖集不同 | 静态 + `-I` 双验证；改完必须重启 |

## 已知边界（未做，别当成已解决）

- **根消息与话题内消息仍不在同一 session**：主框消息本身没有 `thread_id`（话题是回复时才建的），
  所以它复用主框 session；话题内后续消息才有独立 session。属分话题层设计缺口，本轮未动。
- `apply_feishu_cardkit_fix.sh` 是**整文件覆盖**，上游若改了那 7 个文件会有风险 ——
  guard 的基线漂移 WARN/SKIP 是兜底，不是万能。真正稳妥要重新按 hunk 生成补丁。
- 长回答拆卡 / 字节护栏（DSH 借鉴第 1 项）、状态行节流刷新（第 2 项）未实现。
- 网关重启必须由用户在外部执行；agent 重启自己的网关会掐断会话。
