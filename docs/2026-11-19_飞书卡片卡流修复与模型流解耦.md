# Hermes 飞书卡片卡流修复（模型流解耦）

> **日期**：2026-11-19　|　**涉及组件**：Hermes v0.23.2 飞书 CardKit 补丁（`plugins/platforms/feishu/cardkit.py`）
> **性质**：修复记录（DSH 实施修复，豆花归档入库并同步 GitHub）。
> 配置与恢复 SOP 以 [[飞书全量补丁升级维护手册]] 为准。

## 一、问题现象

- 飞书话题里的 Hermes 会话长时间停在「waiting for stream response (0s, no chunks yet)」，单轮回答动辄 10–60 分钟，最久一次卡了近 3 小时。
- 02:57 重启后卡片完全不再更新，且网关日志出现大量「Too many open files」（文件描述符耗尽）。

## 二、根因（py-spy 抓栈实锤）

模型流读取线程并没有卡在 WorkBuddy 的网络读取上，而是被飞书卡片渲染反向堵死：

```
模型流读取 → reasoning 回调 push_thinking → render() → 飞书卡片 API（urllib 同步 HTTPS）
```

- 11 月 17 日加的 CardKit 补丁在模型的流回调里**同步**调飞书接口；飞书请求一慢，模型流就被堵 → 看门狗看到「无 chunk」→ 600 秒杀连接重连 → 再堵，循环。
- 直连实测 WorkBuddy 完全正常（小请求 1.6–2.8 秒、5 万 tokens 流式 5.6 秒、25 个工具定义 3.1 秒、4 并发正常），排除限流、排除网络。

## 三、修复内容（两轮）

### 第一轮：展示层与模型流解耦

- `push_answer` / `push_thinking` / `push_tool` / `set_status` 只更新状态并立即返回；写卡统一交给后台单一渲染线程合并执行（`_schedule_render`）。
- 效果：飞书再慢也堵不住模型流。新增回归测试：卡片接口挂住时，模型回调必须在 2 秒内返回。

### 第二轮：堵住异步化引入的两个新洞

- **失败写入按尝试时刻节流**：原节流只在写入成功后记时间，飞书失败时会以每秒上百次请求重试，把网关文件描述符打爆；现改为每次尝试即记时间，失败重试也受间隔约束。
- **心跳定时器不再直接写卡**：原 `_beat` 每 30 秒直接渲染，与后台写线程并发写同一张卡；现改为只更新状态再排队渲染。
- **新增 `_render_lock` 串行化**：finalize 收尾渲染与后台渲染线程互斥，sequence 不再交错被飞书拒收。
- **失败日志增强**：`instant_put_fallback` 现在带出具体异常内容，便于下次定位。

## 四、验证

- 新回归测试 3 项全部通过：① 卡片接口挂住时模型回调立即返回；② 失败写入受节流（2.5 秒内 think_text ≤4 次尝试、全卡 ≤30 次）；③ finalize 与渲染线程零并发（元素写入最大并发 = 1）。
- cardkit 模块测试 34/34 通过；飞书关联测试（话题回复、设置卡片）63 项全部通过。
- 用修复前源码实测复现过卡死（回调 2 秒内不返回），证明测试有效。
- 2026-11-19 归档时复跑核心 4 测试文件：74 passed / 0 failed（`test_cardkit_scope` + `test_feishu_thread_reply` + `test_setup_feishu` + `test_feishu_setup_cards`）。
