# Hermes 飞书通知唤醒回复落错话题修复（99992402 死分支）

> **日期**：2026-11-19　|　**涉及组件**：Hermes v0.23.2 飞书补丁（`plugins/platforms/feishu/adapter.py`、`plugins/platforms/feishu/cardkit.py`）
> **性质**：修复记录（豆花排查修复、归档入库并同步 GitHub）。
> 配置与恢复 SOP 以 [[飞书全量补丁升级维护手册]] 为准。

## 一、问题现象

- 后台进程（`terminal background+notify`、cron 等）完成后，通知唤醒回合的回复卡片出现在 DM 主窗口，或另起「回复: [IMPORTANT…」新话题，而不是落回原话题。
- 网关重启通知直接丢失：`Restart notification ... was not delivered: [99992402] field validation failed`。
- 正常对话回复从不受影响（都带用户消息锚点），因此该问题长期未被发现。

## 二、根因

1. **飞书 API 事实**：`POST /im/v1/messages`（message.create）的 `receive_id_type` 只接受 open_id/user_id/union_id/email/chat_id 等，**不接受 thread_id**，传入必返 `99992402 field validation failed`。把消息发进已有话题的唯一合法方式：`POST /im/v1/messages/{message_id}/reply` + `reply_in_thread=true`，且锚点必须是话题内已有消息。
2. **死分支**：`adapter.py _send_raw_message` 中「无 reply 锚点但 metadata 有 thread_id 时，用 `receive_id=thread_id, receive_id_type="thread_id"` 建消息」的兜底注释写着 "keeps it in the topic"，实际是无效调用。cardkit 建卡同样只会 `receive_id=chat_id` 裸发主窗口。
3. **受影响消息**：只有「无天然锚点」的消息会走到死分支——后台通知唤醒回合的完成卡（合成事件 `event_message_id=None`）、重启通知等。
4. **旁证**：同文件音频发送路径注释原文 "Audio may fail with 99992402 under thread_id routing: retry as a reply to the thread's last message, then fall back to a plain chat_id send"——音频路径早已修过同款坑，文本/卡片路径从未同步。

## 三、定位方法（可复用）

1. 在 `_send_raw_message` 入口加 ROUTE-DEBUG 探针（INFO 级）：记录每次发送的 `chat_id / thread_id / reply_to / metadata keys / 缓存锚点`。
2. 触发一次后台进程通知复现，对照 gateway.log：ROUTE-DEBUG 参数（thread_id 在、reply_to=None、cache_anchor=None）与 `[99992402]` 报错一一对应，锁定死分支。
3. 教训：**先 grep 错误码，再猜路由逻辑**——99992402 从第一次复现起就在日志里；第一版修复未核对飞书 API 取值约束、照抄死分支同款无效调用，白多一轮重启。

## 四、修复内容（两处，同款模式）

- `adapter.py _send_raw_message`：删除 `receive_id_type=thread_id` 死分支；thread_id 存在且无锚点时，先 `_fetch_last_message_in_thread(thread_id)`（`ListMessage container_id_type=thread page_size=1`）取锚点 → `send_threaded_reply`；取不到锚点才按 chat_id/open_id/user_id 裸发。
- `cardkit.py open()`：建卡无 reply_to 且有 thread_id 时，`GET /im/v1/messages?container_id_type=thread&container_id={thread_id}&page_size=1` 取锚点 → `POST /im/v1/messages/{anchor}/reply` + `reply_in_thread=true`；失败或无锚点回落 chat_id 建卡（卡片不丢）。
- 锚点取自 thread 容器 ⇒ 回复必然加入原话题，不会派生新话题。

## 五、验证

- 回归：核心 4 测试文件 74 passed / 0 failed；两文件 py_compile 通过。
- 实锤 1（原始消息路径）：修复重启后，网关重启通知在与故障完全相同的「thread_id 在、无锚点」条件下成功送达原话题，99992402 消失。
- 实锤 2（卡片路径）：用 cardkit 同款 `_api` 实测 thread 锚点获取 `code=0` 并返回真实 message_id；第二步 reply+reply_in_thread 与所有正常完成卡同一调用形态（日常已验证）。

## 六、回滚与边界

- 回滚：`git checkout -- plugins/platforms/feishu/adapter.py plugins/platforms/feishu/cardkit.py` 后重启网关；或重打本仓库上一版 `patches/feishu_suite_full.patch`。
- 历史上已由通知卡片派生的「回复: [IMPORTANT…」旧话题不会消失（历史消息），修复只保证新消息落位。
- `_fetch_last_message_in_thread` 使无锚点发送多一次 ListMessage 调用（低频路径，可忽略）。
- 若未来飞书官方支持 thread_id 作为 receive_id_type，可简化回单次 create。
